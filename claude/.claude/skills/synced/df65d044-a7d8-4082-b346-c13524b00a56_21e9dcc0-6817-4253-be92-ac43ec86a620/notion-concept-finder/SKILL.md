# Notion Concept Finder

노션의 특정 페이지와 그 하위 페이지 전체에서 개념/키워드를 재귀적으로 찾아주는 스킬입니다.

사용자는 보통 자기가 예전에 정리해둔 노트 어디에 특정 내용이 있었는지를 확인하고 싶어합니다. 그래서 중요한 건 "있다/없다"를 **확실하게** 판정하는 거예요. 대충 검색해놓고 "없는 것 같아요"라고 하면 쓸모가 없습니다. 정말 없는지 끝까지 확인해야 합니다.

응답은 한국어 존댓말로 합니다.

## 워크플로우

### 1. 시작 페이지 찾기

사용자가 준 페이지 제목으로 `Notion:notion-search`를 호출해서 페이지 ID를 얻습니다.

제목이 모호하거나 여러 개가 매칭되면(예: "중대-23-2-1.DB" 같은 복합 경로), 검색 결과를 보고 가장 유력한 걸 고릅니다. 확신이 안 서면 사용자에게 어느 페이지인지 짧게 확인합니다.

### 2. 페이지 트리 구조 파악

시작 페이지를 `Notion:notion-fetch`로 열어서 하위 페이지 목록을 확인합니다. 노션의 fetch 결과는 하위 페이지를 `<page url="...">제목</page>` 태그로 보여주니까 이걸 파싱해서 하위 페이지 URL/ID 목록을 뽑습니다.

재귀적으로 가야 하므로, 각 하위 페이지도 같은 방식으로 열어서 그 아래 하위 페이지가 있는지 확인합니다. 즉, **트리 전체를 탐색**합니다.

**효율적으로 하는 법 — search 먼저, fetch는 좁혀서:** 트리가 크면 모든 페이지를 fetch하는 건 낭비입니다. 먼저 `Notion:notion-search`의 `page_url` 파라미터를 써서 상위 페이지 스코프로 키워드 검색을 돌립니다. 이 검색은 semantic search라 하위 페이지 전체를 (재귀적으로) 커버하는 장점이 있어요. 검색 결과로 후보 페이지를 좁히고, 그 후보들만 fetch해서 정확히 확인합니다.

단, search만 믿지 말고 트리 구조는 따로 파악해둡니다. 못 찾았을 때 "어느 페이지까지 확인했는지" 보고해야 하기 때문입니다.

### 3. 키워드 검색

`Notion:notion-search`를 쓸 때:

- 사용자가 준 개념을 그대로 쓰지 말고 **동의어/유사 표현을 함께 검색**합니다. 예: "nested query" → "nested query subquery 중첩", "다이나믹 프로그래밍" → "dynamic programming DP 동적계획법".
- 한국어 노트일 가능성이 높으면 한국어 용어와 영어 용어를 둘 다 써봅니다.
- 한 번의 검색으로 부족하면 여러 번 검색합니다. 지레 짐작해서 "없음"이라고 결론 내리면 안 됩니다.

### 4. 후보 페이지 내용 정독

검색에서 후보로 나온 페이지는 `Notion:notion-fetch`로 **전체 내용을 읽습니다**. 하이라이트(snippet)만 보고 판단하면 안 됩니다. 하이라이트는 단어 매칭 결과라서 개념이 진짜 있는지 아닌지는 본문을 봐야 알 수 있어요.

본문을 읽을 때 확인할 것:
- 그 개념이 **실제로 다뤄진 내용**인지 (단순 언급 vs 설명)
- 어느 섹션(어떤 heading 아래)에 있는지
- 원문이 어떻게 되어 있는지 (인용할 수 있게)
- 같은 페이지 안에 **여러 섹션**에 걸쳐 나오는지도 확인

### 5. 결과 판정

트리 전체를 다 확인했으면 결론을 냅니다.

**있으면** → 아래 출력 형식으로 답합니다.

**없으면** → "없다"고만 답합니다. 유사 개념이나 다른 상위 페이지(워크스페이스 전체)까지 제안하지 않습니다. 사용자는 그걸 원한 게 아닙니다. 깔끔하게 없다고 하고 끝냅니다.

## 출력 형식

### 찾았을 때 — 2단 구조

**위쪽: 결론 + 위치 목록 (한눈에 보기)**

```
## 검색 결과: '[개념]' — N개 위치에서 발견

[상위 페이지] 페이지 트리에서 '[개념]'을(를) 다음 위치에서 찾았습니다:

1. **[페이지 제목]** > [섹션 heading] — [링크](https://www.notion.so/페이지ID)
2. **[페이지 제목]** > [섹션 heading] — [링크](https://www.notion.so/페이지ID)
3. **[페이지 제목]** > [섹션 heading] — [링크](https://www.notion.so/페이지ID)
```

한 페이지 안에 여러 섹션에 걸쳐 나오면 같은 페이지를 여러 줄로 나눠서 표시합니다. (예: "04. Basic SQL > 3. 문법 > DQL"과 "04. Basic SQL > 5. 예제"가 둘 다 있으면 2줄로)

**아래쪽: 페이지별 원문 + 요약 (상세)**

위 목록에 나온 위치 하나씩 아래 블록을 반복합니다:

```
---

### 📍 [페이지 제목] > [섹션 heading]

🔗 https://www.notion.so/페이지ID

**원문**:
> [해당 부분 원문을 그대로 인용]

**요약**: [그 섹션에서 개념을 어떻게 다루는지 2~3문장]
```

같은 페이지 안에 여러 섹션이 있으면 섹션별로 블록을 따로 씁니다. 페이지 링크는 섹션이 달라도 같은 페이지면 같은 링크를 반복해서 넣어줍니다 (사용자가 어느 섹션에서 클릭해도 그 페이지로 바로 갈 수 있게).

### 원문 인용 분량 제한

원문이 너무 길어서 응답이 뚱뚱해지면 안 됩니다. 한 섹션당 원문은 **최대 1문단(5~6줄)** 정도로 제한합니다. 그보다 길면 핵심만 발췌하고 `[...]`로 생략 표시를 합니다. 섹션이 여러 개라 응답이 길어질 것 같으면 각 원문을 더 짧게(2~3줄) 줄여서 전체 길이를 조절합니다.

### 못 찾았을 때

```
## 검색 결과: '[개념]' 관련 내용 없음

[상위 페이지] 페이지와 그 하위 페이지 N개를 모두 확인했는데 '[개념]' 관련 내용은 없습니다.

확인한 하위 페이지:
- 페이지 A
- 페이지 B
- ...
```

확인한 페이지 목록을 끝에 붙이는 이유: 사용자가 "정말 다 봤나?" 검증할 수 있게. 트리가 크면(20개 이상) 주요 페이지만 나열하고 "외 N개"로 축약해도 됩니다.

## 주의사항

### 재귀 깊이와 효율

깊이 제한은 두지 않습니다. 끝까지 갑니다. 다만 fetch를 무작정 반복하지 말고 먼저 search로 후보를 좁히는 게 좋습니다. 위의 워크플로우 2번을 다시 읽어보세요.

### semantic search의 한계

`Notion:notion-search`는 semantic search라 키워드 정확히 매칭이 아니라 **의미적으로 비슷한 페이지**를 가져옵니다. 그래서 오탐(개념이 없는데 관련있어 보여서 매칭됨)과 누락(키워드를 다르게 쓴 페이지를 놓침)이 둘 다 있을 수 있습니다.

오탐 방어: 후보 페이지는 반드시 fetch해서 본문 확인.
누락 방어: 검색어를 한국어/영어/동의어로 여러 번 돌려보기.

### 원문 인용 시 클린업

노션 fetch 결과는 Notion-flavored Markdown이라 `<callout icon="💡" color="gray_bg">`, `<details>`, `{toggle="true"}`, 이미지 S3 URL 같은 마크업이 섞여 있습니다. 원문 인용할 때는 이런 것들을 제거하고 실제 텍스트만 보여줘서 사용자가 읽기 편하게 합니다.

특히 이미지 URL(AWS S3 signed URL)은 절대 인용문에 포함하지 않습니다 — 길고 지저분하고 곧 만료됩니다. 이미지가 중요한 부분이었다면 "(이미지: 해당 부분에 그림 있음)" 정도로만 표시합니다.

### 노션 링크 포맷

노션 페이지 URL은 `https://www.notion.so/[32자리 페이지ID]` 형식입니다. fetch 결과의 `<page url="...">` 태그에서 URL을 그대로 가져다 쓰면 됩니다. 마크다운 링크 `[텍스트](url)` 형식으로 감싸서 클릭 가능하게 만듭니다.

## 예시

**사용자 요청**: "노션 페이지 '1. DB' 하위에서 nested query 관련 내용 찾아줘"

**스킬이 하는 일**:
1. `notion-search("1. DB")` → 페이지 ID 획득
2. `notion-fetch(page_id)` → 하위 페이지 10여 개 목록 확인
3. `notion-search("nested query subquery 중첩", page_url=page_id)` → 후보 좁히기
4. 후보 "04. Basic SQL" 페이지를 `notion-fetch`로 전체 내용 확인
5. 본문 정독 — DDL, DCL, DML, DQL, Transaction 섹션 있지만 nested query는 없음
6. 다른 유력 후보(03. Relational Operators, 07. DB Programming)도 확인
7. 결과: 없음 → "없다"고만 답하고 확인한 페이지 목록 제시
